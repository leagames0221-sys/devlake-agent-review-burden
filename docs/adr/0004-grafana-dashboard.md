## Context

ADR 0002 fixes the numbers; this ADR fixes the screen. The task: put one dashboard into the Grafana that comes with DevLake, so that a person sees the metrics per AI tool and per way of use, chooses
what is compared and what is counted, and so that a company can adjust the list of tools. The SQL is already tested (ADR 0001, 0002), so the screen takes its SQL from the tested files and does not retype it.
A person must be able to install it without a password (the Grafana API needs the password of Grafana's admin), and the install must be a `plan` then `apply` script (the lesson of U4: a setting made by hand
in screens is not reproducible).

## Decision

### 1. What is copied from the paid service, and what is DevLake's own

The paid service's screen is the model of the choices; DevLake's own dashboards are the model of how a dashboard is built. The names of the company and of the service do not appear on the screen (plan v4 section 1).

| Paid service's screen (saved page) | Ours |
|---|---|
| Five metrics: "PRs merged (throughput)", "Cycle time", "Time to first review", "Time in review", "Batch size" (vendor/swarmia_impact_pr.txt L80-L84; W1) | five tables with these metrics, in Japanese with the English name in brackets |
| Three ways to compare: "AI tools: Each AI tool vs everything else.", "Modes: AI-assisted vs cloud agent vs review agent vs everything else.", "AI used: AI-assisted PRs (based on the tools and modes you select) vs everything else."; "The structure of the tab is the same for all comparisons." (L86-L91; W2) | the variable `comparison`; the panels are the same for the three, only the rows that a table shows change (section 3) |
| "Select which AI tools are included in the comparison." / "Select which modes ... are included in the comparison." (L92-L95; W3) | the variables `tools` and `modes` (several values, All); they select marks (section 2) |
| "There's also an option to include only high-confidence matches in the AI-assisted mode." (L96; W4) | no option: only the marks of high confidence are built (plan v4 S9); the intro text of the screen says so |
| "A single pull request can be associated with multiple AI tools and modes. ... the PR is counted once in the Cursor category and once in the Claude Code category." (L98-L99; W5) | the same count (ADR 0002); the intro text says the sums can be larger than the number of PRs |
| A custom AI tool: a Name, "authors" linked by GitHub or GitLab username, the tool shows as a cloud agent or review agent from the author's activity; an author is linked to one tool only (vendor/swarmia_def_custom_ai_tool.txt L22, L35, L41, L44; W6) | `--custom-tools`: a name and rows (field, pattern); the mode is decided by the field, not written; one `(field, pattern)` belongs to one tool |
| (none) | the variables `include_own_markers` and `first_reaction`, and the three review-burden panels of U1: these are this repo's own |

**A difference to W6.** The service links an author by username. A row here is a regular expression on one of: the login of the PR author, the git name or e-mail of a commit author, the `Co-authored-by` trailer, the login of a reviewer
(the fields of the `identities` list, `docs/agent_identities.md`). It can match more than one author and it can match a person by mistake, so each pattern is anchored by the person who writes it, and the build checks only that it is a regular expression.

### 2. The variables

DevLake's own dashboards give the shape: a query variable `repo_id` (`select concat(name, '--', id) as text from repos where id like 'gitlab%'`, regex `/^(?<text>.*)--(?<value>.*)$/`, multi, All; the first variable of
dl_beta18_Gitlab.json, W13), used as `base_repo_id in (${repo_id})`. Ours is the same with `github%`. The others:

| Variable | Kind | Values | Where it works |
|---|---|---|---|
| `comparison` | custom, one | tools, modes, ai_used | in the closing SELECT of the panel only (section 3); not in the calculation |
| `tools` | custom, several, All | the tools of the `identities` list (read from the SQL when the dashboard is built), and custom tools | **on the marks** (`marks_sel`): a mark is kept when its tool is in the list; also in `all_groups` |
| `modes` | custom, several, All | cloud, assist, review | on the marks: the mode that the mark gives (m1, m2: cloud; m6: review; m3, m4, m5, x1, x2: assist) must be in the list |
| `include_own_markers` | custom, one | 0, 1 | as before (x1, x2 on or off) |
| `first_reaction` | custom, one | review, any | what ends Time to first review (ADR 0002 D16) |

"All" of `tools` and `modes` is the list of all values: the field "Custom all value" is not used. The `identities` list itself is **not filtered**: it also decides who is a bot (`acct`) and which review rows count, which must
not depend on what is selected (D17). The tools of the marks m5 (`cursor`), x1 and x2, which are written in the SQL and not read from `identities`, are filtered as well (`marks_sel` is built on all marks).

**No variable lets a person type text.** Grafana's format option `sqlstring` "escapes `'` in each value by `''` and quotes each value with `'`" (research/v5_grafana/gdoc_variable_syntax.md (https://grafana.com/docs/grafana/latest/dashboards/variables/variable-syntax/) L208-L216; "Variable syntax"), and the page on MySQL template variables recommends it: "use the `sqlstring` format option"
(gdoc_mysql_template_variables.md L139; "MySQL template variables"; W15). It is a quoting rule for the text of a variable; it is not a check of what the text is, and Grafana "doesn't validate the safety of queries" (W20). Therefore: no `textbox` variable, no variable whose value a person types, and every custom variable has `"allowCustomValue": false`. **This does not make a value from the page URL safe:** dashboard variable values can also come from the page URL and reach the query, whatever the selection box allows. `allowCustomValue: false` only keeps a person from adding a value in the selection box. The boundary is the database user (Consequences and limits, and the section "A read-only database user for Grafana").
The default of that field is **true** ("Allow custom values - Enables users to add custom values to the list. Only applies to CSV custom values." gdoc_add_template_variables.md L171; `allowCustomValue: true` in
grafana_v13.2.2_dashboard_types.gen.ts.txt L224-L225, the field at L137-L140; W19), so it is written in the json for every custom variable and also for `repo_id`. A test checks the json: no `textbox` and every `allowCustomValue` is `false`.

**Text variables in the SQL are always `${name:sqlstring}`.** Without a format option the MySQL data source puts a single value in with `'` doubled and **without quotes** ("`return String(value).replace(/'/g, "''")`", grafana_v13.2.2_SqlDatasource.ts.txt L82; and with several values or All
`quoteLiteral`, L79-L80 and L91; `quoteLiteral` = `"'" + value.replace(/'/g, "''") + "'"`, gmysql_main_sqlUtil.ts.txt L69-L71; W16). So the SQL has `${include_own_markers:sqlstring} = '1'` and not a bare `${include_own_markers} = 1`. Only `${repo_id}` stays bare, as in DevLake (W13; a multi variable is always quoted by W16). A test fails when any other bare `${name}` is in the SQL files or in a panel.
The tests replace `${name:sqlstring}` by the rule above (`tools/ai_impact_sql.py`, used by `tests/run_u1.py` and `tools/run_on_devlake.py`); a bare `${name}` is replaced by the W16 rule so that the test can show what a bare variable would do.

**A change to plan v4.** Plan v4 section 5-a said that the companies add and remove tools "by a Grafana variable (regular expression)". That is dropped, because of the paragraph above: a regular expression typed on the screen is a
text typed on the screen. Plan v4 G4 and section 5-a are changed (2026-10-21): the screen selects tools and modes; rows are added or removed by a configuration file when the dashboard is built (section 5).

**Time.** The screen uses the time picker of Grafana, default `now-90d` to `now`, and `"timezone": "utc"` as DevLake's own dashboards do (dl_beta18_Gitlab.json and the dashboard `engineering-throughput-and-cycle-time.json`, W14).
The DevLake database is UTC: its compose file has `TZ: UTC` for mysql (docker-compose.yml L30 in the compose folder used here), and the MySQL data source needs a Session Timezone only when the database is not in UTC
(gdoc_mysql_configure.md L101; W18). `$__timeFilter(col)` is `col BETWEEN FROM_UNIXTIME(a) AND FROM_UNIXTIME(b)` (gdoc_mysql_query_editor.md L83).

### 3. The panels

The screen shows the values at once when it is opened (the owner's rule: the explanation goes elsewhere): the first thing is the row "AI 利用別の PR 指標", open, and its tables are directly under the variables, the three most used side by side (PRs merged, Time to first review, Cycle time: each 8 units wide and 8 high, so that two or more rows of each are in the first screen of a 1280 x 800 window), then the other tables; then the open row "この repo 独自の指標", the closed row "データの確かめ", and the closed last row "この画面の読み方" that holds the text panel. Every table and the dashboard have a one-line description (the i icon). The shape of the rows is that of DevLake's own dashboards (`dl_beta18_Gitlab.json` and `dl_beta18_engineering-throughput-and-cycle-time.json`, key `panels` of the file: a row with `"collapsed": false` and `"panels": []`, the panels after it at the top level ordered by `gridPos.y`; W14 shows their first panel is a text panel and the second a row, which is *not* copied) and for a closed row the type `RowPanel` of Grafana (grafana_v13.2.2_dashboard_types.gen.ts.txt L1172-L1205: `collapsed`, and `panels` holds the panels of a closed row); neither saved DevLake dashboard has a closed row, so the closed rows follow the type only. A first version put the text panel on top and the tables under a closed row; the owner saw no table when he opened it (V7 session).
The SQL of every panel is built, not typed (`tools/build_dashboard.py`):

```
<@common of the SQL file>, metric AS (<@metric>) SELECT * FROM metric WHERE <rows of the comparison> ORDER BY <order>
```

All 13 `@metric` blocks of the two SQL files have no `WITH` of their own (checked by a test), so they can stand in `metric AS (...)`. The metrics of U1 get one more column, `sort_no`, because their own `ORDER BY g.sort_no` is on a column that they do not output;
the column is hidden by a transformation. The rows of each comparison (the key is the first column; written in the build and again, from the specification, in the test):

| Table | tools | modes | ai_used |
|---|---|---|---|
| PRs merged, Cycle time, Time to first review, Time in review, Batch size | `grp LIKE 'tool:%' AND grp NOT LIKE '%\|%'` | `mode:cloud_agent`, `mode:ai_assisted`, `mode:review_agent`, `mode:everything_else` | `mode:ai_used`, `mode:everything_else` |
| PRs merged per week | `grp LIKE 'tool:%\|week:%'` | `grp LIKE 'week:%'` (the columns `merged_*` hold the modes) | the same |
| Cloud agent outcomes | `grp LIKE 'mode:cloud_agent\|tool:%'` | `grp = 'mode:cloud_agent'` | `grp = 'mode:cloud_agent'` |
| U1's three metrics, diagnostics | all rows | all rows | all rows |

The keys of `throughput` and `cloud_agent_outcomes` (ADR 0002) were read in the SQL (`throughput`: `tool:`/`mode:` period rows, `week:<yw>` rows with the mode columns, `tool:<name>|week:<yw>` rows; `cloud_agent_outcomes`: `mode:cloud_agent` and
`mode:cloud_agent|tool:<name>`) and fit the table. The title of Time to first review has the value of `first_reaction`, so a screenshot says what was counted.

### 4. Install: its own provider file, a compose override, no password

Grafana reads dashboards from files that a provider file names; "Each configuration file contains a list of `providers`", and one or more files may be put in `provisioning/dashboards`; "When Grafana starts, it updates or creates all dashboards found
in the configured path." (gdoc_provisioning.md L339-L340, L371; "Provision Grafana"; W10). DevLake's image has one such file, copied with the dashboards into the image: `FROM grafana/grafana:13.2.2`, `COPY ./provisioning/dashboards /etc/grafana/provisioning/dashboards`,
`COPY ./dashboards /etc/grafana/dashboards` (research/v5_grafana/Dockerfile.txt (https://github.com/apache/devlake/blob/v1.0.3-beta18/grafana/Dockerfile) L26-L28), whose provider has `updateIntervalSeconds: 5`, `allowUiUpdates: false`, `path: /etc/grafana/dashboards`, `foldersFromFilesStructure: false`
(dashboard.yml.txt L34, L36, L39, L41; W7). Ours is a second provider file, `dashboards/provisioning/ai-impact.yml`, with the provider name `ai-impact`, one folder, and `path: /etc/grafana/ai-impact`, outside DevLake's path.
It is mounted, with the folder `dashboards/json/` (which holds `ai-impact.json` and nothing else; the provider file is in `dashboards/provisioning/`, as the specification asks), into the `grafana` service by a compose override file. A dashboard built with `--custom-tools` replaces `dashboards/json/ai-impact.json`; a second file with the uid `ai-impact-pr` must not be put in that folder (`plan` checks it), because Grafana would refuse the duplicate uid.

Docker Compose reads a base file and an override file, and entries of `volumes` are merged by the path inside the container ("Entries for `volumes` and `devices` are merged using the mount path in the container", docker_merge.md L187; "By default, Compose reads two files, a `compose.yaml`
and an optional `compose.override.yaml` file." L11-L12; W11). **The saved texts say that `compose.override.yaml` is read; they do not say whether `docker-compose.override.yml` is** (0 occurrences in the two saved pages; docker_compose_application_model.md L42 says only that
`docker-compose.yaml` and `docker-compose.yml` are supported for backward compatibility). DevLake's folder has `docker-compose.yml`, so the script writes `docker-compose.override.yml`; whether Compose read it is what `status` checks (the mounts are in the container), and if not the script stops
and says so; it does not try another name. The long syntax of a volume is used, with `read_only: true` ("Flag to set the volume as read-only.") and `bind.create_host_path: false`; the short syntax "creates a directory at the source path on the host if it doesn't exist",
which would hide a wrong path (compose_services_reference.txt L4930-L4972; W12).

`tools/grafana_install.py plan` changes nothing and prints what `apply` does. `apply` writes the override file and runs `docker compose up -d --no-deps --force-recreate grafana` (U6: the first version had no `--force-recreate`): only the `grafana` container is recreated. **DevLake's start script tries to delete the data sources of Grafana and to create its own when the container starts**:
DevLake's start script runs "Deleting all existing datasources (clean slate)" and creates the data source with `"uid": "devlake-mysql-api"` (entrypoint.sh.txt L159-L167, L174-L188; W8). **On the Grafana 13.2.2 of this DevLake the delete by id answered 404 and the create answered 409** (log lines of 2026-10-21, Appendix B, V6), so the data source that is there is kept, and so is one added by hand (U6 added this observation; the first version of this section said that such a data source is lost). The script calls the Grafana API with the
password `admin` unless `GF_SECURITY_ADMIN_PASSWORD` is set (L139-L142; W9) — this is inside the container and is not our concern; the install does not use it. `status` passes only if all five checks are true: (1, 2) both mounts are in the container, bind mounts, read-only; (3) the sha256 of `/etc/grafana/ai-impact/ai-impact.json` in the container equals the repo file (this proves the bind mount, not what Grafana did with the file); (4) since the container was started the log has the line `finished to provision dashboards` from logger `provisioning.dashboard` (one line for all providers, so it does not say that the provider `ai-impact` was read); (5) the log has no line of logger `provisioning` at level `warn` or `error` that contains `ai-impact` (this covers `ai-impact-pr`, an error about the file `/etc/grafana/ai-impact/...`, and a duplicates warning that names the provider `ai-impact`). **It does not prove that the uid `ai-impact-pr` is in Grafana's database**; looking at the screen does (V7).
**Deviations from the specification, section 4-4.** (a) After a change of the json the specification says to recreate with `docker compose up -d --no-deps grafana`; with an unchanged compose file that command does not recreate a running container, so `docs/dashboard.md` says `docker compose up -d --no-deps --force-recreate grafana` (the 5-second rescan of the provider usually reads the new file, but it is not relied on). (b) `apply` replaces an existing `docker-compose.override.yml` when its first line is the header line that this script writes itself (plan shows the old and the new content as a diff); any other existing override stops the command. Both stay inside what the owner approved: write the override and recreate only the `grafana` container. (c) `status` takes "the time of apply" as the time the container was started (`State.StartedAt`), since apply recreates the container.
The script never reads `.env`, never runs `docker compose config` and never prints `docker inspect` as a whole: the environment of the container has the passwords.

**Why not DevLake's own provider.** Its provider path is `/etc/grafana/dashboards`. In the Grafana of this DevLake the dashboard `grafana-irm.json` is twice under that path (once directly, once under `mysql/`: `tree_dashboards.txt`, `tree_dashboards_mysql.txt`),
the same uid, and the log of Grafana (looked at on 2026-10-21 by the reviewer, and again after the install: Appendix B) shows that DevLake's provider cannot write dashboards ("database write permissions") — a provider that rides on the same path would inherit that. A provider of its own, on a path of its own, does not.

### 5. Custom AI tools and the removal of built-in rows

`tools/build_dashboard.py --custom-tools FILE` (shape in `docs/dashboard.md`) puts rows into `identities` at a marked line (`CUSTOM-TOOLS-INSERT-POINT`) and takes built-in rows out by `(tool, field)`; nothing else of the SQL changes. The mode of a row is decided by
its field (`pr_author`, `commit_author_name`, `commit_author_email`: cloud; `coauthor`: assist; `review_author`: review), the same as the built-in rows, so the file never says a mode. The checks, made at build time (a wrong file stops the build, exit code 2):
the name is `[a-z0-9_-]{1,32}` and is not a built-in name nor `everything_else`; the pattern is lower case, not empty, and has no `'`, `--`, `[[`, `;`, control character, and no `$` followed by a letter, `_` or `{`
(a quote is refused because the pattern is written inside a SQL string; `[[` and `$name` are Grafana's variable syntax; `--` and `;` are refused because `tools/run_on_devlake.py` cuts a line at `--` as a comment in `strip_comments` and sends only one statement); a backslash is doubled when it is put into the SQL (the same writing as the built-in rows);
the pattern is a regular expression for MySQL, checked by `REGEXP_LIKE('', pattern)` on a throw-away container; the same `(field, pattern)` is not in two tools (nor in a kept built-in row), as an author is linked to one tool (W6); a `remove` must match a row,
and may not take the last row of a tool that the SQL names in m5, x1 or x2 (`claude`, `codex`, `copilot`, `cursor`, `devin`), because a PR would then carry a tool that has no row. The file in the repo is built without custom tools.

### 6. What was not done, and why

- **Teams as a way of comparing** and **the low-confidence marks** are not built (plan v4 section 10, S9).
- **PostgreSQL** is not built (`sql/mysql` only).
- **Other format options for strings.** A stronger format such as `percentencode` was thought of; the saved texts do not say what it escapes, so it is not used.

## Alternatives considered

- **Grafana's HTTP API** (`POST /api/dashboards/db`). Rejected: it needs the password of Grafana's admin, which this install does not use or read; the install would not be a script that a person runs without a secret.
- **Import by hand in the screen** (upload the json). Rejected: not reproducible, and it is the kind of setting by hand that U4 gave up.
- **Build a new image of DevLake's dashboard** (the Dockerfile above with our json copied in). Rejected: the install would then depend on our image and not follow the upgrades of DevLake's.
- **Put the json into DevLake's provider path** (`/etc/grafana/dashboards`). Rejected: its provider cannot write in this DevLake today (section 4), and our json would sit under the same uid check as the doubled `grafana-irm.json`.
- **A textbox / regular-expression variable for adding tools on the screen** (plan v4 section 5-a). Rejected: section 2.
- **A stronger format option for the strings.** Section 6.
- **Filter `identities` by `tools`.** Rejected: `identities` decides who is a bot; the mutant V4-01 shows the bot flag changing with the selection.

## Consequences and limits

- **The database user is the real boundary.** Dashboard variable values can also come from the page URL and reach the query. Grafana "doesn't validate the safety of queries", and says to "ensure the database user you specify has only `SELECT` permissions on the relevant database and tables" (gdoc_mysql_configure.md L49; "Configure the MySQL data source"; W20). The default data source user of DevLake's Grafana is the MySQL user `merico`, which has write rights (a SELECT on the privileges, 2026-10-21). ## A read-only database user for Grafana (U6, 2026-10-21)

**The problem.** Dashboard variable values can also come from the page URL and reach the query, and the data source of DevLake's Grafana uses `merico`, a user with write rights. Grafana "doesn't validate the safety of queries" and says to "ensure the database user you specify has only `SELECT` permissions on the relevant database and tables" (`research/v5_grafana/gdoc_mysql_configure.md` (https://grafana.com/docs/grafana/latest/datasources/mysql/configure/) L49). So the boundary that holds is the right of the database user, and the dashboard cannot be that boundary.

**Decision.** Grafana's data source `devlake-mysql-api` (the uid that the 23 places for a data source in `dashboards/json/ai-impact.json` use) is changed to a database user `grafana_ro` who has `SELECT` on `lake.*` and nothing else. Three parts:

1. **`tools/grafana_readonly_user.py`** (`plan` / `apply` / `status`; standard library and the docker CLI). `apply` is typed by the owner of the DevLake; `plan` and `status` change nothing and can be run by anyone. It uses the line `GRAFANA_DB_RO_PASSWORD` of the `.env` in the compose folder, or makes a value with `secrets.token_hex(24)` (hex digits only,
   so no `$`) and adds one line after checking that `.env` ends with a newline; then it sends, on standard input to `mysql` as root inside the `mysql` container, `CREATE USER IF NOT EXISTS 'grafana_ro'@'%' IDENTIFIED BY '<value>'; ALTER USER 'grafana_ro'@'%' IDENTIFIED BY '<value>'; GRANT SELECT ON lake.* TO 'grafana_ro'@'%';`.
   MySQL 8.4 manual: the host part defaults to `'%'` (`research/v6/mysql84_grant_excerpt.txt` (https://dev.mysql.com/doc/refman/8.4/en/grant.html) L104); an administrator "first uses CREATE USER to create an account" and then GRANT (L106, example `CREATE USER ... IDENTIFIED BY 'password'` L108); `ON db_name.*` is the database level (L386); `ALTER USER` sets the password again, so a second run
   leaves `.env` and the database with the same password. The root password is expanded inside the container (`-p"$MYSQL_ROOT_PASSWORD"`, the way `tools/run_on_devlake.py` does it for `merico`). A mysql error prints only `ERROR nnnn`, because the text of an error can contain a part of the statement and so the password.
   `status` checks, as root: `SHOW GRANTS FOR 'grafana_ro'@'%'` is exactly ``GRANT USAGE ON *.* TO `grafana_ro`@`%` `` and ``GRANT SELECT ON `lake`.* TO `grafana_ro`@`%` `` (the form that MySQL prints, `research/v6/mysql84_show_grants_excerpt.txt` (https://dev.mysql.com/doc/refman/8.4/en/show-grants.html) L10, L20, L24); `SHOW PROCESSLIST` (all connections are visible with the PROCESS right, `research/v6/mysql84_show_processlist_excerpt.txt` (https://dev.mysql.com/doc/refman/8.4/en/show-processlist.html) L12;
   `Host` is `host_name:client_port`, L86) has from the IP of the grafana container at least one connection of `grafana_ro` and none of `merico` (the connection exists after a panel was loaded, so look after opening the screen); and it records, without judging, how many times the log since the start of the container has the two lines of DevLake's start script (`Datasource created successfully`, `Datasource already exists; keeping existing one`) and how many lines of Grafana's own request log are a `POST /api/datasources` with status 409 and a `DELETE /api/datasources/<id>` with status 404.
2. **`dashboards/provisioning/datasources/ai-impact-ro.yml`**, a Grafana data source provisioning file: uid `devlake-mysql-api`, name `mysql`, type `mysql`, url `mysql:3306`, database `lake`, user `grafana_ro`, `secureJsonData.password: $GRAFANA_DB_RO_PASSWORD`. "If the data source already exists, Grafana reconfigures it to match the provisioned configuration file" (`gdoc_provisioning.md` L90-L92), an environment
   variable is read with `$ENV_VAR_NAME` (L43-L45), and for a value that may contain `$` the single-`$` form is the one to use (L72). Fields added to the specification's list: `access: proxy`, `isDefault: true` (both as the start script of DevLake creates its data source, `entrypoint.sh.txt` L174-L188) and `editable: false` (so the screen cannot change the user back).
   The file is mounted read-only by `tools/grafana_install.py --readonly-db` at `/etc/grafana/provisioning/datasources/ai-impact-ro.yml`, a name of its own: the file that DevLake's start script writes (`datasource.yml`, `entrypoint.sh.txt` L121-L137) is not touched.
3. **`tools/grafana_install.py --readonly-db`** adds that mount and, in the `environment` of the `grafana` service, `GRAFANA_DB_RO_PASSWORD`, `MYSQL_USER: grafana_ro` and `MYSQL_PASSWORD`, both passwords as `"${GRAFANA_DB_RO_PASSWORD:?run tools/grafana_readonly_user.py apply first}"`. Docker Compose merges `environment` and "locally defined values" (the override) win (`docker_merge.md` L151);
   it reads the `.env` of the project folder by default (`docker_variable_interpolation.md` L68, L80) and `${VAR:?error}` stops with the message when the value is missing (L52). The `MYSQL_USER` and `MYSQL_PASSWORD` lines are for the other way: when DevLake's start script does create its own data source it takes the user and the password from these two variables (`entrypoint.sh.txt` L44-L57),
   so the data source is `grafana_ro` whichever way the start script goes. An existing override that has these lines is not replaced by one without them, in `plan` or in `apply`, unless `--drop-readonly-db` is given (so that the documented way "build the json again and install again" cannot silently remove the read-only lines by a forgotten flag; without them a Grafana that is set up again, with a new volume, would get the data source of `merico` again).
   `apply` recreates the container with `docker compose up -d --no-deps --force-recreate grafana` (the earlier `apply` had no `--force-recreate`: an unchanged compose file does not recreate a running container). If Docker Compose stops because the `.env` line is missing, `apply` puts the old override back (a wrong override would make `docker compose up` of the folder stop; `docker compose ps -q` still works).
   `--anonymous-viewer` (only together with `--readonly-db`; `GF_AUTH_ANONYMOUS_ENABLED: "true"`, `GF_AUTH_ANONYMOUS_ORG_ROLE: Viewer`, names from Grafana's rule `GF_<SECTION>_<KEY>` and `[auth.anonymous]` `enabled`, `org_role`; `research/v6/gdoc_anonymous_auth.md` (https://grafana.com/docs/grafana/latest/setup-grafana/configure-security/configure-authentication/anonymous-auth/) L44-L53, `gdoc_configure_grafana.md` L79-L92) is for the recording of the video and is not applied together with this change;
   `plan` prints the warning. `status --readonly-db` also checks that the third mount is in the container and read-only.

**The line in `.env` also reaches two other containers.** `devlake` and `config-ui` have `env_file: ./.env` (in the compose file used for U4), so they receive `GRAFANA_DB_RO_PASSWORD` when they are created the next time. They do not use it. The owner is told in `plan`.

**Rejected.**
- *Only the environment variables `MYSQL_USER` and `MYSQL_PASSWORD`, so that DevLake's start script creates the data source as `grafana_ro`.* The start script tries to delete all data sources and to create its own, and when that fails it keeps the old one ("Datasource already exists; keeping existing one", `entrypoint.sh.txt` L226-L233). It fails on this machine: the log of Grafana (`docker compose logs grafana`, 2026-10-21) has `DELETE path=/api/datasources/1 status=404 ... handler=notfound` (the delete by id finds no route in this Grafana 13.2.2) and the answer `POST /api/datasources status=409`
  (Appendix B, V6), so nothing is deleted and the data source that is there stays as it was (`merico`). The two variables are still set, as the second way, but they are not what the change rests on.
- *A data source of our own with another uid, for our panels only.* DevLake's own dashboards (70 files, below) would stay on `merico`, so the Grafana would still run a user who can write for every other screen; and our dashboard uses the uid `devlake-mysql-api` in 23 places, which the build has fixed (`tools/build_dashboard.py` L50).
- *Make the screen safe in the dashboard* (`allowCustomValue`, a format option). A value that comes from the page URL does not pass the selection box, so `allowCustomValue` cannot be the boundary; the saved text does not say what a stronger format option escapes (section 6).
- *Take the write right away from `merico`.* DevLake itself writes `lake` with `merico`; that would stop DevLake.

**Why a read-only user does not break DevLake's own screens.** The 70 dashboard files of the tag `v1.0.3-beta18` (6 in `grafana/dashboards` and 64 in `grafana/dashboards/mysql`; the image copies `./dashboards` to `/etc/grafana/dashboards`, `Dockerfile.txt` L28) were saved with `gh api` and counted by a script of the author (not published; `research/u6/dl_beta18_dashboards/` holds the saved files): **70 files, 69 with SQL, 869 SQL strings** (rule: the `rawSql` of the panel targets, 762; the `query` of the template variables of type query, 102; and a `definition` that differs from its query, 5; the one annotation query of `github-copilot-dora-correlation.json` is not counted, and was read as well), 564 start with `SELECT` and 305 with `WITH`, **0 write statements** (no INSERT, UPDATE, DELETE, REPLACE INTO, DROP, CREATE, ALTER, TRUNCATE, GRANT,
REVOKE, RENAME, LOAD, CALL, INTO OUTFILE; the string functions `REPLACE(` and `INSERT(` are not counted), a second pass over every string except the values of the keys `description`, `content`, `title`, `text`, `label`, `name` and `info` found no further string that looks like SQL (a select, insert, update, delete or with word and a from word) beyond the 869, and a third pass over every one of the 29,292 strings of the files, those keys included, for two-word write patterns (insert into, update .. set, delete from, replace into, drop/create/alter + table, database, view, index, schema or user, truncate, grant/revoke .. on, into outfile or dumpfile) had 0 hits. The count is for the saved files; it does not say what a plugin or a person's own panel sends. The state of Grafana itself (users, folders, dashboards) is in its own SQLite file `grafana.db` in the `grafana-storage` volume, not in `lake`.

**What stays readable, and what was not solved.**
- `SELECT` on `lake.*` still lets a person who can open a URL of the screen read **every table of `lake`** through the SQL that the URL value can change: the tables of the connections (the tokens in them are stored encrypted, but the rows are readable), the raw tables of the GitHub data, and the tables that hold people's logins and names. The change stops a **write**, not a **read**.
- The SQL is still built from the URL value (a value that is not in the options can still give a SQL error). A heavy query still costs time. `grafana_ro` has no right to write, to create or drop, to read files, or to grant.
- While `--anonymous-viewer` is on (for the recording only), a person without a login can open the screen and send such a query. `plan` and `apply` of `--anonymous-viewer` stop unless every port of `grafana` and `config-ui` in the compose file of the folder is published on `127.0.0.1` (DevLake's own compose file, `research/v3/upstream/install/docker-compose.yml.txt` (https://github.com/apache/devlake/releases/download/v1.0.3-beta18/docker-compose.yml) L39 and L72, publishes `3002:3000` and `4000:4000` on all interfaces, and `config-ui` proxies `/grafana`, L43 and L77; the compose file used for U4 binds both to `127.0.0.1`). Switch it off afterwards and check (a) the override has no `GF_AUTH_ANONYMOUS`, (b) the container started after the override was updated, (c) a browser without a login gets the login page.
- The Grafana admin password and the Grafana API are not part of this change.
- **Observed on 2026-10-21 (after the owner ran `tools/grafana_readonly_user.py apply` and `tools/grafana_install.py apply --readonly-db`):** `SHOW GRANTS FOR 'grafana_ro'@'%'` was exactly the two lines ``GRANT USAGE ON *.* TO `grafana_ro`@`%` `` and ``GRANT SELECT ON `lake`.* TO `grafana_ro`@`%` ``; `tools/grafana_install.py status --readonly-db` passed 6 of 6 checks; after the screen had been opened, the connections from the grafana container were `grafana_ro` 2 and `merico` 0 (the same `status` before the change: `grafana_ro` 0, `merico` 3). A later run of both `status` commands on the same day gave the same result.
- **Taking the override away, or `--drop-readonly-db`, does not put the data source back.** A provisioned data source stays in Grafana's database after its file is gone unless `deleteDatasources` or `prune: true` is used (`gdoc_provisioning.md` L93-L99; the file `ai-impact-ro.yml` sets neither), and DevLake's start script keeps an existing data source (404/409). So the data source stays `grafana_ro` with `editable: false`. Going back to `merico` is not covered by this repository and not described in the saved texts; a person has to change the data source before the database user `grafana_ro` is dropped. (The first version of the texts of `plan` and of `docs/dashboard.md` said that the data source goes back to the user of DevLake's compose file; this was wrong.)
