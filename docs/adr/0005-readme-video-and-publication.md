# ADR 0005: The base (DevLake), the language and naming of the README, the video, the author name, and the repository name

Status: accepted (2026-10-21). Scope: `README.md`, `docs/images/`, the demo video (kept outside this repository until publication), the history of this repository at publication. 

Sources that are saved files of the author's research folder are named as in ADR 0004, each with the public URL of the original; the research folder is not published (see `docs/glossary.md`). The records of this repository are cited by file.

## Context

The tool is finished and tested (ADR 0001 to 0004). Two things are left before it can be shown: a README and a video that a person who decides about buying or building (the person in charge of AI-driven development) can read without knowing the code, and a history that can be published. Five decisions were taken for that. The first is the one that the rest of the repository stands on (why DevLake is the base), and it had not been written down in one place.

## Decision

### 1. The base: Apache DevLake, with MySQL, the standard library only, and DevLake's own Grafana

- **DevLake is the base.** It is free (Apache-2.0), a company runs it on its own machine, and it already holds the tables that the metrics need: `pull_requests`, `pull_request_comments`, `accounts` (ADR 0001, Context). It also brings the connection to GitHub (the import of two repositories took 7 minutes 43 seconds with three data entities; `docs/validation/u4-real-data.md` section 2) and a Grafana with a MySQL data source. No dashboard of DevLake v1.0.3-beta18 separates PRs by AI tool with marks taken from the PR itself: of the 70 dashboard files of the tag ([`grafana/dashboards`](https://github.com/apache/devlake/tree/v1.0.3-beta18/grafana/dashboards); one pair has identical content), the AI-related ones (Copilot, Cursor, Kiro, and the two Claude Code dashboards) read the usage tables of each tool (`_tool_copilot_*`, `_tool_cursor_*`, `_tool_kiro_*`, `_tool_claude_code_*`), and the 869 SQL strings of the 70 files have 0 hits for `Co-authored-by` and for bot names (README, section "既存の物との違い"). The counting rule of the 869 (a script of the author, not published, over the 70 saved files): the `rawSql` strings of the panel targets (762), the `query` strings of the template variables of type query (102), and the `definition` of a variable when it differs from its query (5); an annotation query is not counted. ADR 0004 uses the same number and rule.
- **The work is an addition to DevLake, not a change of DevLake.** The code is outside DevLake: SQL files, a script that sets up the import through DevLake's REST API (`tools/devlake_configure.py`), a script that adds the PR assignees (`importer/`), and a dashboard that is put into Grafana by files and a compose override. The owner decided on 2026-10-20 that contributions to DevLake itself are not needed for the purpose (build the same analysis in house, for free); the plan of this work was changed for that. Nothing here prevents a later proposal to DevLake.
- **MySQL only.** DevLake's own default is MySQL, the real-data check (`docs/validation/u4-real-data.md`) ran on it, and every number was checked there. PostgreSQL is out of scope: the SQL uses MySQL functions that PostgreSQL does not have in that form. PostgreSQL has no `YEARWEEK` ([date functions, version 15](https://www.postgresql.org/docs/15/functions-datetime.html)), and `REGEXP_LIKE` exists only from version 15 ([version 15](https://www.postgresql.org/docs/15/functions-matching.html); the page of version 14 does not list it); `percent_rank()` exists in both ([window functions](https://www.postgresql.org/docs/15/functions-window.html)). A second database would need a second test run that was not made.
- **Python standard library only for the product** (SQL, the scripts, the tests). Nothing has to be installed to run or test it (only Python and Docker), no package can be changed under it, and every script can be read in one sitting. The video tool (`produce_video.py`) uses `requests` and Playwright and is therefore kept outside the repository (decision 3).
- **DevLake's Grafana is used** (not a new Grafana, not a web application of our own): it is already in DevLake's compose file, it reads the same MySQL, and a company that runs DevLake has it. The screen is installed by provisioning files (ADR 0004).

### 2. The README is in Japanese, and the name of the paid service appears in two sections only

- The README is in Japanese; the ADRs and `docs/` stay in English (the existing text), and `docs/importer.md` was already Japanese. The readers named in the plan are persons in charge of AI-driven development in Japanese companies. A Japanese README with English technical records behind it lets the reader of the README stop at the README and a reviewer go on to the ADRs.
- **The name of the paid service and of its company is written only in the section of the definition table and in the section of the cost comparison** (the rule of this work: the README is a material for "buy or build", not an advertisement of a replacement). Everywhere else the README says "有料の AI 分析サービス". Reason: the work is offered as a material for "buy or build", and the name is needed only where a row is compared with a source (table) and where a price is quoted (cost). Also not used: words that run the service down, "same quality" as a guarantee, and anything that reads as a partnership. The README says that the internal numbers of the paid service cannot be compared, because the service is not under contract. A check (`verify_readme_numbers.py`, a script of the author that is not published) maps every number of the README to its record, and asserts that the number of lines with the name outside the two sections is 0.
- **The section "既存の物との違い" names existing things** (the GitHub `issue-metrics` action, `mitzu-io/pr-metrics`, `dervalp/fieldnote`, and the AI dashboards of DevLake itself), with the generic term for the paid service. A reader needs at least one named alternative and the difference to it. The author's working plans (not published) had two statements that did not fit (one asked for the names of the existing things, including the paid service, near the top; the other asked for no company name outside two sections). The second wins, and the names of the free things give the reader the named alternatives.
- **The cost is written with its condition.** "Software cost 0 yen" holds for the software; the machine, the care, and, for a large organization, Docker Desktop's license are the company's (the Docker documentation, [the page at commit a356e2a](https://github.com/docker/docs/blob/a356e2a80e84ccc7cfbfa371bb1167db2bab5c2f/content/manuals/subscription-billing/desktop-license.md), retrieved 2026-10-21, saved as `research/v6/gh_docker_desktop-license.md`; in the repository of the Docker documentation the page is now at `content/manuals/subscription-billing/desktop-license.md`, the old path `subscription/` is only an alias in its front matter).
- The limits include one found while building the read-only user: dashboard variable values can also come from the page URL and reach the query, so with `grafana_ro` the screen can only read, but it can read every table of `lake` (ADR 0004, "A read-only database user for Grafana"). It is written in the README, not only here.

### 3. The video: the Grafana screen only, recorded with Microsoft Edge, four phases, placed at publication

- **The scenes are the Grafana screen only** (open, the three ways of comparing, how the first reaction is counted, the own markers). The README is not recorded: there is no standard way to show a Markdown file in a browser for this kind of recording, and the repository is not yet public. The video is 115.4 seconds long (18 scenes), read by the voice AivisSpeech (まお おちついた), in plain words for persons who are not engineers (Roman letters and symbols are written in kana for the voice; every narration line is at most 30 characters; the mora list that the voice engine returns was compared with the intended reading for every line).
- **The method is the one of the author's earlier video script** (a private repository, not published; the script was copied and only the scenes, the browser, the credit and the checks were changed). The rule it follows, in one line: *record the screen scene by scene, measure how long the screen takes to settle after each action, and start the voice only after that time*, in four phases: (1) one WAV of narration per scene, (2) the recording, with the settle time of every scene measured, (3) each WAV padded with silence of that length, (4) joining video and audio with ffmpeg, burning in the subtitles, and holding the last frame for the credit. The script is kept in the working folder, outside this repository, because it uses `requests` and Playwright (decision 1: the product is standard library only).
- **Deviation: Edge instead of Playwright's own Chromium.** The method records with Playwright's Chromium. Playwright's browsers are not installed on this machine, and nothing is installed for this work (zero cost, no installation without the owner). The installed Microsoft Edge is used (`launch(channel="msedge")`). Playwright's recorder also asks for its own `ffmpeg` binary; the `ffmpeg` that is already installed (the one phase 4 uses anyway) is copied into a browsers folder of the working folder and given to Playwright through `PLAYWRIGHT_BROWSERS_PATH`. The page looks the same (Grafana in a 1920 x 1080 window).
- **Deviation: x264 `crf 18` instead of `crf 23`, and the bitrate rule is not met at `crf 23`.** A rule of thumb for videos made with this method is a bitrate of at least 450 kbps at `crf 23`; below it the video is probably a row of still pictures. At `crf 23` this video has 413 kbps (the same recording and narration, encoded again for the check): **it does not meet the rule**. The reason is that the screen is mostly still: the tables stay on the screen, and between the actions only the subtitle changes. The picture does change where the actions are: 100 frames with a picture change (scene-change score above 0.003) in 26 separate moments of the video (the dropdowns, the tables that are loaded again, the scrolling; the list of times is in the output of the video check, and the frames of every scene were looked at). `crf 18` is used so that the small Japanese text of the tables stays sharp (653 kbps). That number is not a proof of motion and is not given as meeting the rule.
- **The credit text is the sentence fixed for this video** ("公開 repo 2 本（期間 2026-09）を手元の DevLake に取り込んだ実データ。"), and not the usual "synthetic data only", which is not true for this video. A second line credits the voice. The credit follows the last scene as a 7-second hold, so that it does not cover a subtitle.
- **Recording needs a time without a login.** For the recording only, `tools/grafana_install.py --readonly-db --anonymous-viewer` switches on anonymous viewing (role Viewer, bound to 127.0.0.1 only; the script refuses other ports), and after the recording the override is written again without it and three things are checked (no `GF_AUTH_ANONYMOUS` in the override, the container started after the override was changed, a browser without a login gets the login page). The video shows no login and no person; the opening shows Grafana's loading page for about three seconds.
- **Placement is decided at publication.** The file is not in the repository. At publication the owner chooses where it is kept (a release of the GitHub repository, or a link in the README); the README gets one line then. The owner listens to the video before that.

### 4. The author name is replaced before publication, and the hashes are mapped afterwards

- The e-mail address of every commit is already the GitHub no-reply address (`ID+USERNAME@users.noreply.github.com`, GitHub's documentation, [Email addresses reference](https://docs.github.com/en/account-and-profile/reference/email-addresses-reference), saved as `research/v6/gh_email_addresses_reference.md` L45-L47). The name field of every commit had been the owner's real name. The only name that may identify the author is the name of the GitHub account, so the name field was replaced by the GitHub user name.
- **How**: the owner makes a copy and saves `git log --reverse --format='%H %s'` outside the repository; sets `user.name` in this repository only; and rewrites the history with `git rebase --root --exec 'git commit --amend --no-edit --author="<name> <noreply address>"'`. `--exec` runs the command after every commit (git-rebase manual, [git-scm.com/docs/git-rebase](https://git-scm.com/docs/git-rebase), saved as `research/v6/git_rebase.adoc` L551-L555), `--root` rebases the root commit as well (L575-L578). `--reset-author` is not used: it also renews the author's time (git-commit manual, [git-scm.com/docs/git-commit](https://git-scm.com/docs/git-commit), saved as `research/v6/git_commit.adoc` L138-L142), and `--author=` keeps it. The committer's time becomes new; this is said to the owner first. A stop in the middle is undone by `git rebase --abort`. Afterwards the count of the real name in `git log --format='%an <%ae> | %cn <%ce>'` must be 0.
- **Hashes**: a rewrite changes every hash. The documents of this repository name commits (for example `docs/validation/u4-real-data.md`, ADR 0002, ADR 0004, this ADR). After the rewrite the old and new lists of hashes (30 commits, no merge commit) were matched by position, and the subject of every commit was checked to be equal in both lists. Every old hash that a file names (20 places in 4 files) was replaced by the new hash of the same length, in one new commit. The mapping of all 30 hashes is kept in a working file that is not published. The text of a commit message cannot be changed without another rewrite, so a commit message may still name an old hash: one commit message does (see the appendix); the table there gives the new hash of that old hash, so that a reader can follow it.
- After the rewrite, the checks that depend on the history (the wording of the commit messages, the date of the last commit, secrets and names in every commit) were run again. The owner did the rewrite.

### 5. The name of the repository stays `devlake-agent-review-burden`

The name of the repository is used in nine places in six files (the NOTICE, ADR 0004, `docs/importer.md`, `importer/github_pr_assignees.py`, `tools/grafana_install.py` and its test), and in the first line of the compose override that `tools/grafana_install.py` writes: the script replaces an existing override only when its first line is that header (ADR 0004, section 4), so a changed name would make the script refuse the override that is installed now. The name says what the tool is for (the review burden per agent, on DevLake); it does not name any company. It stays.

## Alternatives considered

- **Base: `issue-metrics` as the base.** Rejected. It is a GitHub Action that reads a search query and writes a report as an issue; it has no database, no Grafana, no tables of reviews and comments to join, and no AI-tool grouping (its README: the metrics are time to first response, to first review, to close, in label, in draft). Making it the base would mean building the storage, the screen and the grouping here.
- **Base: collecting the data from GitHub by our own code.** Rejected. DevLake already collects PRs, reviews and comments with the settings and the rate handling, and the real-data check (297 PRs) ran on its tables. A collector of our own would need its own tests for the pagination, the deletion of removed rows and the limits, and it would not be the data a DevLake user already has.
- **PostgreSQL as a second target.** Rejected for now (see decision 1). A SQL that is written once and run on two engines would need a common subset that does not exist for `REGEXP_LIKE` and the median method used here.
- **Third-party packages for the scripts** (a MySQL client, a test framework, a template library). Rejected: an installation step for every reader, and the tests do not need them. The cost is some more lines of code written by hand (for example the fake `docker` of the tests); the price was accepted.
- **A Grafana of our own, or another screen tool.** Rejected: one more service to run, and DevLake's own dashboards could not be shown next to it.
- **README in English only, or in both languages.** Rejected: the first reader is Japanese, and a second language doubles what has to be kept equal. The ADRs stay in English.
- **The name of the paid service in the lead of the README.** Rejected (decision 2): it reads as "a replacement of that service", and the work is a choice between two ways.
- **Video: record the README; record with Playwright's own browser; shoot the screen by hand.** Rejected in order: there is no standard way to show Markdown; the browser is not installed and nothing is installed here; a hand recording is not repeatable.
- **Author name: leave the real name, or use a new repository from a clean state.** Rejected: the name must not be published; a new repository would lose the history that the ADRs refer to. Rewriting the author only keeps the commits, the dates and the messages.
- **A new repository name.** Rejected (decision 5).

## Consequences

- The README can be read by a person who does not know the code; every number in it is mapped to its record by `verify_readme_numbers.py` (a script of the author that is not published), and the check fails on a number that is not mapped or does not match. A number that changes in a record (a test total, a count) has to be changed in the README as well; the script shows it.
- The README says what is not done. The limit about the URL and the database rights stays until Grafana accepts only values of the list in the URL (not under our control).
- The video is not part of the repository's history; the repository does not grow with it. It was made with a deviation from the pipeline's browser (Edge), which is written down here. A later rebuild needs Grafana with anonymous viewing on and the voice engine, and ends with the three revert checks.
- The rewrite of the author changes every hash. The hashes inside the documents are replaced in one commit; the hashes inside commit messages stay old and are explained by the table of the appendix. The old history (a copy outside the repository) is kept by the owner.
- The name of the repository is fixed.
